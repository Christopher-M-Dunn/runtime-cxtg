# ADR-016: `<cxid, sid>` naming for `cxsel`'s context-index field, departing from spec's `IDX`

**Block(s):** all

The draft spec uses "idx" for two different things: the context index
within a CXID (`cxsel`'s `IDX` field) and the word-index into a context's
state data (`cxsidx`). Guy Lemieux flagged this collision as issue #1 in
his 2026-08-18 mailing-list kickoff of the unpriv state management
discussion (`tech-composable-custom-extensions`, message #568).

This project already resolved it in code: the Phase 1 design
(`docs/superpowers/specs/2026-05-22-phase1-csr-instruction-scaffolding-design.md`,
`docs/superpowers/plans/2026-05-22-phase1-csr-instruction-scaffolding.md`)
defines `cx_sel_t` with a `.sel.sid` bitfield (`CXSEL_SID_BITS`,
`CXSEL_SID_POSITION`) for what the spec calls `IDX`.
`qemu-cxtg/target/riscv/cpu_bits.h`'s `cxsel` layout comment: `[15:8] SID
(spec calls this IDX) | [7:0] CXID`.

Christopher Dunn proposed the same `<cxid, sid>` pairing to the TG mailing
list on 2026-08-26 (message #576) — "i've been using <cxid,sid> to avoid
confusing myself" — referring to what he already chose for this project.

**Problem:** `docs/CXTG_QEMU_Action_Plan.md` uses `IDX` throughout, not
`SID` — it disagrees with the code. The Action Plan is read first at the
start of any new block, so the mismatch will keep propagating `IDX` into
new specs/plans.

**Decision:** use `SID`, not `IDX`, as this project's name for `cxsel`'s
context-index field. Update the Action Plan text (`IDX` → `SID`, `<CXID,
IDX>` → `<cxid, sid>`) before writing the next block's spec.
